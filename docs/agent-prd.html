01背景与目标

巨鑫是一家外贸制造企业(购物手推车、多用途手推车、露营拖车、户外家具),核心业务链路是:访客提交询盘 → 邮件通知业务员 → 人工跟进。海外买家的常见问题高度结构化 —— MOQ、装箱量、集装箱装载、包装、能否改颜色/OEM —— 而这些答案恰好已存在产品库(specs.containerLoad、moq、variants…)。

目标:用一个售前 AI 助理把业务员重复回答的问题前置到官网自动答掉,并把高意向访客转化成一条更完整的结构化询盘,同时对超出能力边界的问题(报价/库存/交期)干净地转人工。

  • 业务目标 —— 降低业务员重复答疑负担;提升询盘质量与转化。
  • 工程目标 —— 在真实业务系统中落地一个有工具调用、可评测、带人工确认业务动作的 Agent；再以真实企业资料扩展 RAG。

02定位与非目标

这是全文最重要的一节 —— 边界定义了"不像玩具"与"过度承诺"之间的线。

定位:售前助理(pre-sales),不是成交客服。 它帮买家问清产品、做选型、并留资,不负责报价与交易。

05系统架构

前端聊天气泡 → Agent 编排 → 工具层(包一层现有接口)→ 存储 / 知识 / 模型。数据库与图片走既有云服务。

图 1 · 当前系统架构。Agent 的产品工具直调共享 productService；询盘由 Agent 生成 lead 草稿、买家在 LeadCard 明确确认后走现有 /api/inquiries，不把写操作交给模型自动执行。

06Agent 状态设计

当前刻意保持状态最小化：浏览器负责本轮会话上下文，LangGraph 只负责单次请求内的 Agent/Tool 消息循环；不建设 conversations 集合。

① 浏览器会话状态（不落库）

{
  messages: [...],         // ChatWidget 内存状态；每轮随 /api/chat 重发
  pendingLead?: {          // 模型输出的 lead 草稿，经前端解析成确认卡
    name, email, summary
  }
}

② 当前 LangGraph 控制流

START → agent(Qwen Plus + tools)
              ├─ 有 tool_calls → ToolNode → agent
              └─ 无 tool_calls → END

产品意图首轮可强制 tool_choice:'required'
最终文本再做产品链接对库校验 → 失败则强制重试 → 仍失败则安全兜底

③ 询盘动作状态（Human-in-the-loop）

Agent 输出 lead 草稿
→ ChatWidget 解析
→ LeadCard 展示并允许买家编辑
→ 买家点击确认
→ POST /api/inquiries
→ inquiry 落库
→ 后台异步 geo / 邮件 / emailed 状态回写

当前没有 create_inquiry LangGraph 节点，也不让模型直接执行写操作；用户确认是事务边界。

避坑

"查询中 / 回答中"不是业务状态，是前端 UI status。若后续做流式输出，以事件驱动展示即可，不需要为它扩展持久化状态。

07工具定义

工具输入输出映射
getProductidOrSlug单个产品（specs / variants / features）productService.getPublicByIdOrSlug
searchProductscategory?, keyword?, color?产品列表（精简字段）productService.listPublic

硬约束

规格/数字问题必须走 getProduct / searchProducts 取真值，禁止模型自答。询盘属于写操作，模型只能生成包含买家真实姓名、邮箱和需求摘要的候选 action；未经过买家确认不得落库或发邮件。

落地状态

searchProducts / getProduct 已实现并端到端跑通（agent/tools.js，直调 productService）；getProduct 已含结构化特征字段（features、loadCapacity、material）。P4 询盘闭环也已落地：模型输出 lead 候选块，前端解析为 LeadCard，买家编辑并确认后复用现有 inquiry API / inquiryService 完成落库与异步邮件。它刻意不是 LangGraph 写入 Tool。

08RAG 设计

本节是 P5 规划，当前尚未实现。硬规格继续走 tool calling（精确）；公司简介、认证、OEM/ODM、包装出货、FAQ 等软信息再走 RAG。内容量可以小，但 pipeline 与评估必须真实。

  • 第 0 步 —— 先把软内容写出来(现状 company.mock.js 太薄),这是真正的工作量。
  • Pipeline —— chunk → embedding → 存 Atlas Vector Search → 相似度检索 → 注入 prompt。
  • 评估 —— 20 条软问题做 before/after,拿到"命中率从 X 提到 Y",对上 JD 的"RAG 准确率提升经验"。
决策

功能上内容少、静态块就够;但为 RAG + 向量库 关键词,升级成真 RAG(Atlas Vector Search / FAISS)。定位为"小而真"的 pipeline。

09模型选型

关键不是抽象的“智商”，而是 tool calling 可靠性 + 多语言 + 不幻觉 + 延迟/成本。不同意图分级用模型，但产品真值路线不能为了快而牺牲工具调用。

方案免费Tool Calling可部署用途
Qwen Plus按 DashScope 额度/计费✔ 当前可靠主线✔ 托管 API产品查询、推荐、规格问答
Qwen Flash按 DashScope 额度/计费⚠ 不承担产品主线✔ 托管 API纯寒暄快速通道
其他 OpenAI-compatible 模型视供应商必须跑 45 条 eval视供应商成本/延迟候选，不直接宣称可替换

用 OpenAI 兼容 SDK 写,endpoint 可换 —— "模型无关、可切换"本身是工程加分点。

实际落地（v0.3）

最终用 阿里云 DashScope · Qwen（OpenAI 兼容端点）——因为部署位置决定可用性：原计划的 Gemini/Groq 在国内不可达。主线用 qwen-plus（tool calling 可靠）；纯寒暄走 qwen-flash 快车道（~0.9s）做速度分级。实测：qwen-flash 对"推荐"类软请求会跳工具、编假型号，故产品路线必须用 plus。换模型只改 3 个 env。省钱更快的候选：deepseek-v4-flash（便宜、支持 tool calling、有 prompt 缓存正好治"大 prompt 每轮发两遍"）—— 但换模型前必须跑 eval 防幻觉倒退。

10防幻觉与安全边界

实际落地成防御纵深四道（单一措施都堵不死 LLM 编造，详见架构讲解页）：

  • ① 强制工具 —— 产品意图命中就 tool_choice:'required'，逼模型必须查库、不许凭感觉编型号。
  • ② 工具返回瘦身 —— 搜索列表只给型号/链接/热销/MOQ，颜色/尺寸等易串的数字只从单条 getProduct 取，防多条间张冠李戴。
  • ③ Prompt 收紧 + temperature 0 —— 只准说工具返回的字段，功能/卖点一律不许编；越界(价格/库存/交期)硬转人工留资。
  • ④ 出口链接对库校验（最硬） —— 回复发出前把每个 /products/<id> 拿去库里核，有假链接→强制重试→仍假则安全兜底。假链接绝对到不了用户，不依赖"永远堵不全"的关键词正则。
  • 语言一致 —— 每轮按买家语言在末尾追加强指令，防中英混排/语言跑偏。
  • 防注入 —— system prompt 后端注入，前端只发消息内容，只信任工具返回。
  • 无关/敏感话题不涉入 —— 政治/地缘(台湾)/宗教/医疗/其他公司/编程等不表态、不展开，礼貌转回产品；情绪类先一句共情再温和转回。当前由 system prompt 约束，并纳入 Agent eval 回归；未来可增加 Flash 分类器 + 本地固定模板，让高风险挡回不依赖主模型自由生成。
诚实的局限 & 优雅方向

现在这套有效但是"反应式打地鼠"。更优雅 = "LLM 只选、代码渲染真值"：LLM 只输出要推荐的产品 id，后端按 id 从库取真实名/链接/规格由代码渲染，LLM 结构上没机会吐假产品，可替掉大半补丁。列为 P3 重构方向。

11会话策略（不持久化）

模型本身无状态。当前由 ChatWidget 在浏览器内持有 messages，每次请求把本次会话所需历史一起发送，因此可以理解“第一款”“它”“换成蓝色”等追问。

  • 不建设 conversations 集合，后端不保存完整聊天记录，也不宣称长期记忆。
  • 刷新页面后历史可丢失，这是当前明确接受的范围取舍；它不影响产品 Tool Calling 与询盘闭环的核心面试价值。
  • 接口中可选的 conversationId 当前只原样回传，可作为请求关联标识，但不用于查库、记忆或数据关联。
  • 只有买家在 LeadCard 中确认的 name / email / message 才进入 inquiry；不把完整聊天文本附带落库。

15技术栈与部署

  • 前端 —— React + Vite + Tailwind；ChatWidget 持有多轮 messages，LeadCard 承担询盘确认。
  • 后端 / Agent —— Node.js + Express + LangGraph.js；Agent 作为现有后端模块运行，模型经 OpenAI-compatible SDK 接入 DashScope。
  • 数据与外部服务 —— MongoDB/Mongoose 保存 products 与 inquiries；阿里云 OSS、geo、SMTP 邮件沿用现有全栈能力。Atlas Vector Search 属 P5 规划。
  • 封装 —— 多阶段 Dockerfile 先构建前端，再由后端静态托管，生产形态是单个 web 容器；Compose 仅额外提供本地开发 Mongo profile。
  • 质量 —— Vitest + Supertest + Testing Library + ESLint；GitHub Actions 分别执行后端 lint/test 与前端 lint/test/build。
  • 部署 —— 目标是单个 Docker Web Service，外接 Atlas / OSS / DashScope / SMTP；不宣称已拆分为独立 Agent 微服务。

16范围纪律(不做什么)

明确不碰 —— 超预算且易在面试翻车

多 Agent 编排 · 手写 ReAct 脚手架 / LangChain 老 AgentExecutor · 微调 / 自训 embedding · 复杂 RAG（re-rank / query 改写）· LangGraph 复杂状态机 · 重型 eval 平台 · 为简历故事强拆微服务。

定位是"全栈工程师把 AI 功能扎实落进真实系统",不是 Agent 研究。深度不是战场 —— 扎根 + 闭环 + 测量才是。ReAct 当概念理解即可,用原生 tool calling / LangGraph 实现。
